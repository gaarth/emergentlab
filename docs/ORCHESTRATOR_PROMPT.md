1. **Work in phases. Each phase ends with its tests green.** Do not start the next phase with a red test. If a test cannot pass in 5 minutes, write down why in `NOTES.md`, stub the behaviour, mark the test `xfail` with the reason, and move on. A shipped stub beats a perfect blocker.
2. **Ask me nothing you can answer by reading the spec.** Only interrupt for: a missing API key, a dependency that will not install, or a contract change (which requires both of us).
3. **Never edit `tree.json` schema after phase 0 is committed.** If you believe the schema is wrong, add optional fields; never rename or remove.
4. **Commit after every green phase** with the message `phase N: <what>`. Push. The other person pulls.
5. **Print a 3-line status after each phase:** what passed, what is stubbed, what is next.
6. Use subagents where the work is parallel (e.g. writing tests while writing code), but you own integration.
7. The environment variable `TRACK` tells you which slice to build: `contract`, `lab` (Muaaz), or `viewer` (Gaarth). Do only that track, plus anything in Phase 0.

## PHASE L — Lab track (TRACK=lab, Muaaz)

### L1 — `ca.py` substrate (target 19:05)

Build per IMPLEMENTATION_MUAAZ.md section 1.

Tests (`tests/test_ca.py`):
- `parse_rule("B36/S23") == ({3,6},{2,3})`; lowercase and `B3/S` (empty survive) both parse.
- A single glider under `B3/S23` on a 32-torus has exactly 5 alive cells after 4, 8, 40 steps (translation only, no growth).
- A block (2x2) under `B3/S23` is unchanged after 50 steps.
- `count_copies` returns 1 for a lone seed, 2 for two copies placed far apart, and 2 when the second copy is rotated 90° and mirrored.
- `evaluate("B36/S23", HIGHLIFE_REPLICATOR_SEED, steps=60)` returns `copies >= 2` — this is the sanity check that the fitness can detect replication at all. If it fails, the demo cannot show a win; fix `count_copies` before anything else.
- `evaluate("B2/S", seed)` (Seeds, explosive) returns `stable == False` and `fitness < copies`.
- Performance: `evaluate` on a 64-torus for 60 steps completes in < 0.5 s (`pytest --durations=5`).

### L2 — Sandbox (target 19:15)

Build `run_sandbox` per section 2.2, as an importable function.

Tests (`tests/test_sandbox.py`):
- Valid `experiment_code` returning `[ca.evaluate(r, seed) for r in rules]` yields a list with `fitness` on every item and no `frames` key.
- Code that raises → `RuntimeError` whose message contains the original exception text.
- Code with `while True: pass` → times out in ≤ 21 s and raises.
- Code that `import os` / `open()` / `import requests` → rejected before execution (simple AST or string check; note the limitation in NOTES.md). This is a hackathon, not a prison; a basic check is enough.
- Indented `experiment_code` (4 leading spaces on every line) still runs (dedent is applied).
- The temp file is deleted even on failure.

### L3 — Loop with a fake model (target 19:25)

Build `lab.py` per section 2.2, with `ask_fable` injectable so tests can replace it.

Tests (`tests/test_loop.py`) — use a `FakeFable` that returns scripted proposals:
- 3 scripted proposals → `tree.json` gains 3 nodes, ids `n3..n5` (continuing from the small fixture), each with `parent`, `depth = parent.depth + 1`, `frames` as 4 existing PNG paths, `replay` filled, `status == "done"`.
- A proposal with broken code → node saved with `status: "error"`, `error` non-empty, and the *next* prompt's text contains that error string (assert on the captured user message).
- A proposal whose `rules_to_test` are all already tested → node marked `error` with "already tested" in the message, no sandbox call.
- `best_node_id` updates only when fitness strictly improves.
- `replay.size` on every done node equals the `size` used by `ca.evaluate` (64). Assert against a module constant `ca.GRID_SIZE`, not a literal.
- Anti-stagnation: after 4 done nodes with no improvement, the next user message contains `DIRECTIVE` and the top-3 ids.
- Every 8th done node → message contains "rule family you have NOT tried".
- `save()` is atomic: monkeypatch `os.replace` to assert it is used; a reader opening `tree.json` mid-write never gets invalid JSON (run 200 saves in a thread while parsing in another).
- `STOP` file present → loop exits before the next proposal and `write_paper` is called (mock it).
- JSON robustness: `ask_fable` given text with prose before/after the JSON and with ```json fences still returns the dict; given garbage three times returns `None` and the loop continues without appending a node.
- Resume: run the loop twice on the same `tree.json`; node ids continue and `best_node_id` is not reset.
